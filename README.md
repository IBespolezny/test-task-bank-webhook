# Subscription Payment Webhook

FastAPI-сервис, принимающий уведомления банка об оплате подписки.
Без ORM: доступ к PostgreSQL — через сырой `psycopg2`, миграция — один
`.sql`-файл.

## Запуск

```bash
docker-compose up --build
```

Поднимутся два контейнера:
- `db` — PostgreSQL 16, при первом старте автоматически накатывает `init.sql`
  (создаёт таблицы и тестового пользователя `id=42`);
- `app` — FastAPI на `http://localhost:8000` (можно поменять в .env).

Открыть автоматическую документацию можно по url `http://localhost:8000/docs`

`GET /health` — проверка живости.

## Какие решения приняты и почему

**Миграция на пустой базе**
В задании было сказано сделать миграции простым .sql файлом. Это файл `init.sql` стартует при первом создании контейнера.

**Идемпотентность (проблема дублирования оплат при повторных вебхуках банка).** 
Вебхук с `payment_id` может прийти повторно, нельзя добавлять его в БД без проверки на наличие,
поэтому `payment_id` уникальное значение. Дальше платёж можно только обновить на `CONFIRMED` (не обратно),
это реализовано с помощью `ON CONFLICT (payment_id) DO UPDATE SET`, если
конфликт строк, то обновляем или не обновляем статус. Дальше вызываем активацию подписки
или не выызваем в зависимости от статуса.

**Атомарность (проблема падения сервера или сети).** 
`payments` и `subscriptions` — таблицы одной и
той же БД, поэтому для атомарности достаточно одной обычной
транзакции: `INSERT` платежа и `UPSERT` подписки выполняются в одном
`conn`, коммитятся вместе одним `commit()`, поэтому при отключении сети
или ошибке на сервере данные просто откатятся обратно и при повторном запросе банка
добавятся в БД корректно.

**Продление подписки.** Если у пользователя уже есть активная
подписка, новая оплата продлевает её от **текущей даты окончания**, а
не от текущего момента:
`expires_at = GREATEST(subscriptions.expires_at, now()) + interval '30 days'`.
Так пользователь не теряет уже оплаченные дни при досрочном продлении.
`GREATEST` в Postgres игнорирует `NULL`, поэтому та же формула
корректно работает и при первой активации.

**Миграции без Alembic.** Один `init.sql`, который запускается при
старте приложения. Минус: он работает только на пустой Базе,
поэтому отдельно нужно создавать дирикторию и контейнер с миграциями,
но в этом задании такое специально не сделано.

**Пул соединений.** `psycopg2.pool.ThreadedConnectionPool`, а не
`SimpleConnectionPool`: uvicorn выполняет синхронные path-функции в
пуле потоков, значит к пулу соединений возможен параллельный доступ из
нескольких потоков — `ThreadedConnectionPool` для этого потокобезопасен.
ThreadedConnectionPool грубо говоря даёт подключения по порядку.

**Серис оплаты**
Бизнес-логика, а именно обновление подписки вынесено в отдельный сервис,
чтобы не загружать эндпоинты и тестировать код отдельно (на будущее).

**Структура проекта**
Проект состоит из дириктории `app`, виртуального окружения, докер файлов и зависимостей.
Деление на дириктории и модули в самом `app` сильно не производил из-за масштабов проекта это излишне.
Но базовая структура с чёткой точкой входа создана.
