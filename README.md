# Subscription Payment Webhook

FastAPI-сервис, принимающий уведомления банка об оплате подписки.
Без ORM: доступ к PostgreSQL — через сырой `psycopg2`, миграция — один
`.sql`-файл.

## Запуск

```bash
docker-compose up --build
```

Поднимутся два контейнера:
- `db` — PostgreSQL 16, при первом старте автоматически накатывает `init.sql`
  (создаёт таблицы и тестового пользователя `id=42`);
- `app` — FastAPI на `http://localhost:8000`.

Проверить:

```bash
curl -X POST http://localhost:8000/webhook/payment \
  -H "Content-Type: application/json" \
  -d '{"payment_id": "abc-123", "user_id": 42, "amount": 4900, "status": "CONFIRMED"}'
```

Повторная отправка того же тела запроса вернёт
`{"status": "already_processed", ...}` и не изменит БД.

`GET /health` — проверка живости.

## Структура

```
init.sql            — схема БД (миграция)
query.sql           — запрос из п.4 ТЗ
app/main.py         — эндпоинт POST /webhook/payment
app/db.py           — пул соединений psycopg2 + транзакция на запрос
app/schemas.py      — валидация входящего JSON (pydantic)
docker-compose.yml, Dockerfile
```

## Какие решения приняты и почему

**Идемпотентность (п.2).** `UNIQUE(payment_id)` в таблице `payments` +
`INSERT ... ON CONFLICT (payment_id) DO NOTHING`. Проверка "было ли уже
такое уведомление" сделана constraint'ом в БД, а не `SELECT`-ом из
Python перед `INSERT`: при двух параллельных одинаковых запросах
`SELECT`-based проверка ловит гонку (оба запроса могут увидеть
"записи ещё нет" и оба вставить), а `ON CONFLICT` — нет, конфликт
разрешает сама БД на уровне индекса.

**Атомарность (п.3).** `payments` и `subscriptions` — таблицы одной и
той же БД, поэтому для атомарности достаточно одной обычной
транзакции: `INSERT` платежа и `UPSERT` подписки выполняются в одном
`conn`, коммитятся вместе одним `commit()` в конце запроса (см.
`app/db.py::get_db`). Если процесс упадёт между двумя `INSERT`, всё,
что не закоммичено, укатится обратно при следующем подключении к
соединению — Postgres откатывает незакоммиченную транзакцию сам.
Отдельный Saga/Outbox-паттерн здесь избыточен: он нужен, когда данные
размазаны по разным базам/сервисам, а тут всё в одной БД под одним
`BEGIN/COMMIT`.

**Продление подписки.** Если у пользователя уже есть активная
подписка, новая оплата продлевает её от **текущей даты окончания**, а
не от текущего момента:
`expires_at = GREATEST(subscriptions.expires_at, now()) + interval '30 days'`.
Так пользователь не теряет уже оплаченные дни при досрочном продлении.
`GREATEST` в Postgres игнорирует `NULL`, поэтому та же формула
корректно работает и при первой активации.

**Миграции без Alembic.** Один `init.sql`, который официальный
`postgres`-образ сам исполняет при первом старте контейнера (файл
лежит в `docker-entrypoint-initdb.d/`). Для одной таблицы и тестового
задания отдельный самописный migration-runner — overhead; в реальном
проекте с растущей схемой взял бы несколько пронумерованных файлов
(`001_init.sql`, `002_add_index.sql`, …) + таблицу
`schema_migrations`, отслеживающую применённые файлы.

**Пул соединений.** `psycopg2.pool.ThreadedConnectionPool`, а не
`SimpleConnectionPool`: uvicorn выполняет синхронные path-функции в
пуле потоков, значит к пулу соединений возможен параллельный доступ из
нескольких потоков — `ThreadedConnectionPool` для этого потокобезопасен.

**Что не сделано намеренно.** Если банк вторично присылает тот же
`payment_id`, но с другим статусом (например, сперва `PENDING`, потом
`CONFIRMED` с тем же id) — текущая реализация проигнорирует второе
уведомление, потому что ключ идемпотентности — сам `payment_id`. В
реальной интеграции стоит уточнить у банка контракт: может ли
`payment_id` переиспользоваться с разным статусом, и если да — менять
стратегию на `ON CONFLICT DO UPDATE` с проверкой перехода статуса
(например, обновлять только если старый статус `PENDING`).
